# V0.1 演示案例与验收矩阵

状态：首批冻结候选  
版本：0.1.0  
目标：先用可解释的虚构数据验证规则，再扩展评测集

## 1. 统一输入约定

除特别说明外，Claim 为“张某于 2026-03-15 向李某支付人民币 50,000.00 元”，允许日期窗口为前后3日，交易均为银行转账。`Txxx` 为规范交易 ID。

## 3. 验收口径

### 功能验收

- D01 可从导入到报告完整运行。
- D02、D03、D04 的覆盖金额与状态完全匹配预期。
- D05-D11 能展示对应风险并阻止不当自动纳入。
- D12 必须阻止人工确认。
- D13-D15 能保留事实，不把缺失或退款自动解释成法律结论。

### 可追溯验收

- 每个 Claim 有起诉书和/或陈述的来源定位。
- 每个 Transaction 有原始 CSV 行号和文件哈希。
- 每个 included 金额能反查到唯一交易。
- 报告包含系统建议、人工决定、版本、理由、校验结果和免责声明。

### 稳定性验收

- Mock 模式不联网可重复运行。
- 同一输入重复运行，确定性计算结果一致。
- LLM 提取失败时进入人工补录，不产生伪造 Claim。
- 任何阻断校验错误都不能创建 `HUMAN_CONFIRMED`。

## 4. 基线比较计划

V0.1 评测至少比较四种方法：人工审查、通用大模型直接回答、固定提示词、“资金链证审”工作流。每种方法在相同输入材料上记录：

- 候选交易召回率；
- 错误纳入率；
- 覆盖金额计算准确率；
- 证据来源引用正确率；
- 冲突和缺口发现率；
- 单案处理耗时；
- 重复运行输出一致性。

首批 D01-D15 用于规则和开发测试；冻结后另建不参与开发的盲测集，避免选择性报告。

## 5. 失败案例记录格式

每次失败至少记录：案例 ID、输入摘要、预期、实际输出、失败环节、是否影响金额、人工处置、修复版本和是否加入回归测试。不得删除失败记录或只保留成功截图。
